# Prismatic Platform capability map (Fáze 0 audit)

**Date**: 2026-08-05/06. **Status**: read-only research artifact, output of Fáze 0 of
[`docs/missions/2026-08-05-prismatic-platform-integration-master-prompt.md`](../missions/2026-08-05-prismatic-platform-integration-master-prompt.md),
governed by
[`docs/adr/prismatic-platform-integration.md`](../adr/prismatic-platform-integration.md)
and `AUTH-2026-08-05-PLATFORM-SCOPE` in `AGENTS.md`. Nothing in
`~/dev/prismatic-platform` was edited, written to, or committed to produce this
document. No Prismatic capability was actually invoked against a live external
registry or database — every row below is an **entry in a capability map**, not
a completed integration.

## vomaste.cz baseline (measured, 2026-08-06)

26 entity dossiers, 955 claims, 658 sources, 93 cases, 202 gaps, 334 relations,
527 shared entities.

## Method and how to read this document

`~/dev/prismatic-platform` is a 96-app Elixir/OTP umbrella (~15,900 source
files) — far too large to hand-verify exhaustively in one pass. This audit
combines direct file-by-file verification (registries, DD schemas, storage
export, config/secrets — the items vomaste's own pre-T-028
`docs/dossier-audit/PRISMATIC_SOURCING_TODO.md` had already assumed were real)
with three parallel, independent, read-only research passes covering the
remaining OSINT, domain-model, and storage/orchestration apps. Every "real" or
"stub" claim below traces to a `.ex` file someone actually opened — moduledoc
claims were **not** taken at face value, and several rows below exist
specifically because a moduledoc's claim and its code disagreed. Where a
capability could not be verified (too large a surface, time-boxed), that is
stated explicitly rather than presented as confirmed.

**The single most important finding of this audit**: vomaste's own
`PRISMATIC_SOURCING_TODO.md` named `mix prismatic.osint.czech.business`,
`mix prismatic.osint.czech.property`, and
`mix prismatic.osint.legal.investigation` as tools to run for
already-authorized dossiers (Macinka/Turek, Klempíř, Schillerová, etc.). All
three are demo/mock implementations — they generate synthetic data
(`:rand.uniform`, a hardcoded "Adam Vasina" fixture person, fabricated
"digital footprint"/"darknet intelligence" prose) rather than calling any real
registry. **None of them may be used as a source for any vomaste claim.** This
is exactly the failure mode the Oto Klempíř authorization entry in `AGENTS.md`
already flagged once for a satire-section URL — the same discipline applies to
code, not just web sources: a command name reading as real is not evidence
that it is.

## Overall recommendation

### Strongest reuse candidates for the first real export-contract implementation (Fáze 2)

1. **`PrismaticDd.Schemas.{EntityRecord,EvidenceItem,FetchRecord,RelationshipRecord}`** — use as the direct design template for the export contract's `entity_candidate`/`claim_candidate`/`source_candidate`/`relation_candidate` record shapes. The custody-ratchet pattern (machine-derived evidence must carry a `tool_run_id`/`fetch_record_id`/`artifact_hash`) maps almost one-to-one onto vomaste's own "every claim needs a named, dated, opened source" rule, and it is real, tested, and enforced at the changeset level — not aspirational.
2. **`PrismaticOsintCore.{ProvenanceArtifacts,ProvenanceAssertions}`** — the closest existing analog to the raw-zone contract shape Fáze 2.2 specifies (content hash, source URL, retrieved timestamp, request fingerprint), already content-addressable via SHA-256.
3. **The ARES and Justice.cz HTTP clients** (`PrismaticOsintSources.Adapters.Czech.Ares`/`.AresTesla` and the `or.justice.cz` family) — genuinely real, genuinely useful, and directly match registries vomaste's contributors already verify manually today. Pick **one** canonical implementation per registry first; three independent ARES clients and four independent `or.justice.cz` clients exist with no deprecation marker, and picking the untested one (`Prismatic.Registries.AresClient`, whose own test file is `# Add your tests here`) instead of the tested one (`PrismaticOsintSources.Adapters.Czech.Ares`, tested against real IČOs) would be an easy, costly mistake.
4. **`PrismaticDd.Bulk.Orchestrator` + `CheckpointStore`** — the strongest existing template for vomaste's own `prismatic:plan`/`run`/`--resume`/`--dry-run` requirements: real ETS+disk-persisted checkpointing, per-group dry-run, and resumability that skips already-processed entities. Worth mirroring architecturally even though it cannot be called directly (it requires Prismatic's own Postgres/ETS runtime).
5. **`PrismaticAudit`** (Ecto-backed paper-trail versioning) — the most trustworthy audit-log implementation found anywhere in the platform; a good design reference for the `reviewed_by`/`reviewed_at`/`run_id` promotion audit trail Fáze 2.8 requires.

### Traps — things that look reusable but are not

- **`mix prismatic.osint.czech.business`, `.czech.property`, `.legal.investigation`** — read as real Czech-registry investigation tools (and vomaste's own pre-existing TODO doc assumed they were). All three are synthetic demo CLIs generating random or hardcoded fixture data. Must never be used as a source for any claim.
- **`prismatic_osint_eu_institutions`** — all 13 adapters (Parliament, Commission, TED, EUR-Lex, ECB, ECJ, EDPS, EEAS, Court of Auditors, Ombudsman, Transparency Register, Eurostat, agencies) fabricate data behind real-looking base URLs, caching, rate-limiting, and circuit-breaker infrastructure. This is the platform's clearest example of "confidently fake" — the surrounding engineering quality is not evidence the underlying data is real.
- **`prismatic_property_intelligence/cuzk_client.ex`** — makes a genuine live HTTP call to the real ČÚZK cadastral endpoint, then **discards the response and returns a hardcoded fictional person** ("Mgr. Tomáš Rašovský", born 1969-11-15) regardless of what was actually fetched. This is arguably the single most dangerous entry in this table for vomaste specifically, since several dossiers have live property claims (Turek's Dubeč/Strahov property, Tünde Bartha's flat, Zuzana Mrázová's Bílina apartment) that a real-looking-but-fake ČÚZK hit could silently corrupt if wired in without the code being read first.
- **`prismatic_perimeter`'s "court-admissible," "tamper-evident," "ECDSA-signed" evidence chain** — zero Ecto schemas, pure in-memory GenServer state lost on process restart, and the claimed ECDSA signature is a SHA3-256 hash with a source comment admitting it's simplified. A durable, cryptographically-signed evidence chain does not currently exist anywhere in Prismatic despite the doctrine language claiming one does.
- **PEP/sanctions bulk screening (`mix dd.seed.pep`/`dd.seed.sanctions`)** — the real underlying sanctions adapters exist (`ofac_sdn.ex` with genuine Jaro-distance fuzzy matching, `eu_sanctions.ex`, `un_sanctions.ex`), but `PrismaticDd.Bulk.Orchestrator`'s dispatch for these two groups calls `PrismaticOsintSources.Adapters.Global.OpenSanctions.search_cz_peps/2` and `.search_cz_entities/2` — **a module that does not exist anywhere in the codebase**. It fails soft (silent no-op), so a "0 entities processed" result from this exact command looks identical to a clean negative sanctions check. Do not treat a zero result from this command as a verified negative screen until the wiring is fixed upstream.
- **"Fuzzy matching" claims in general** — `prismatic_osint_czech_legal`'s `EntityResolver`/`Correlation` modules explicitly claim fuzzy name matching in their moduledocs but implement exact-normalized-string grouping only. A genuinely fuzzy matcher does exist (`prismatic_czech_autocrawler/l2_synthesis/entity_resolver.ex`, real Levenshtein+Jaccard), but it auto-merges with no review-gate distinction, which directly conflicts with the master prompt's explicit "no auto-merge on identity collision" requirement (Fáze 2.6) — it would need a review gate bolted on before any reuse, not a straight wrap.
